# Scheduling poll

The scheduling feature extends `ScheduleEvent` rather than using a separate application. An owner creates an event at `/admin/schedule`, receives a public `/schedule/<random-token>` link, and confirms one final meeting after collecting availability.

## Data model and slot strategy

`ScheduleDate` stores each date's local working range. `ScheduleSlot` persists the generated UTC slots and exposes a random UUID to the browser. Persistence keeps slot IDs stable, makes availability rows relational, and lets the server reject timestamps or slot IDs from another event. `ScheduleSelection` stores only selected slots with a unique participant/slot constraint.

Slots are generated by iterating UTC between two local midnights in the event's IANA timezone and filtering by the configured local range. This correctly represents daylight-saving gaps and repeated local hours. The event stores an IANA zone (for example `America/Chicago`), never a fixed abbreviation or offset.

## Sessions and authorization

Participants have no account. Creating a response issues a random, HTTP-only, SameSite cookie whose server-side SHA-256 digest is stored in `ScheduleParticipantSession`. Every availability request checks both the event and participant session, so a session for one event cannot be used for another. Owner operations require an authenticated staff account and are scoped to the event's creator.

## Availability and ranking

The browser collects selections locally and submits them in one batch. The server confirms that every submitted UUID belongs to the current event, replaces that participant's selections transactionally, and rate limits submissions.

Aggregation and best-time ranking run on the server. For every possible start, the algorithm requires every interval needed for the configured meeting duration to be consecutive and selected by a participant. Candidates rank by available count, percentage, then earliest UTC start. The owner can save their own availability, which is included in the same calculation.

## Confirmation and calendar files

Confirmation persists a `ConfirmedMeeting` with explicit UTC start/end timestamps. The public page shows it in either the event timezone or the participant's selected browser timezone. The ICS endpoint emits UTC `DTSTART`/`DTEND` values and the Google Calendar link uses the same instants, avoiding offset arithmetic in the client.

## Security boundaries

Public API payloads exclude database event IDs, owner information, participant emails, and participant lists. Public schedule routes are marked `noindex, nofollow`. Event tokens use cryptographically secure URL-safe random values. The UI renders input as text; it never injects event or participant data as HTML.
